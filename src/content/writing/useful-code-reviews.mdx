A reviewer needs to understand the problem before judging the solution. A concise change description can save more time than a long tour of the implementation.

## Explain the behavior

Describe what was happening, why it mattered, and what happens after the change. Include the assumptions that would make the solution incorrect if they stopped being true.

## Keep a change coherent

A review is easier when it answers one main question. Separate unrelated refactoring when possible. When a refactor is necessary for a fix, explain that dependency.

## Show useful evidence

A test result matters when it covers a real failure mode. Name the scenario you checked and any limit of that check. This lets the reviewer focus on the risks that remain.
