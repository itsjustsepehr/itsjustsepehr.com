تا وقتی ایجنت فقط پیشنهاد کد می‌ده، ریسک کار تقریباً شبیه یک دستیار معمولیه. اما وقتی می‌تونه دستور Shell اجرا کنه، پکیج نصب کنه، فایل تغییر بده و به سرویس‌های بیرونی درخواست بفرسته، دیگه فقط با یک ابزار تکمیل کد طرف نیستیم؛ یک فرایند اجرایی داریم که باید براش مرز دسترسی تعریف کنیم.

ممکنه داخل README یک ریپوزیتوری، یک Issue یا حتی یک صفحهٔ وب دستور مخربی پنهان شده باشه. اگر ایجنت اون متن رو به‌عنوان دستور معتبر بپذیره، تأیید گرفتن برای هر فرمان هم همیشه جلوی آسیب رو نمی‌گیره. راه‌حل فقط نوشتن Prompt بهتر نیست؛ باید محیطی رو محدود کنیم که ایجنت داخلش اجرا می‌شه.

در این مقاله از **Eclipse Enclave** به‌عنوان یک نمونهٔ تازه از معماری Sandbox استفاده می‌کنم. هدفم معرفی یا تبلیغ یک ابزار خاص نیست؛ می‌خوام ببینیم یک محیط اجرای ایجنت چه مرزهایی لازم داره و کجاها نباید به عبارت «ایزوله» اعتماد بیش از حد کنیم.

## چرا این موضوع الان مهم شده؟

در ۱۹ نوامبر ۲۰۲۶، Eclipse Foundation پروژهٔ متن‌باز و مستقل از فروشندهٔ [Eclipse Enclave](https://newsroom.eclipse.org/news/announcements/eclipse-foundation-launches-eclipse-enclave-10-bringing-security-and-choice) رو معرفی کرد؛ محیطی که برای اجرای خودمختار ایجنت‌های کدنویسی طراحی شده. هر نشست در Container جدا اجرا می‌شه و دسترسی فایل، شبکه و اطلاعات احراز هویت باید از قبل مشخص بشه.

چند سیگنال رو هم کنار این خبر بررسی کردم:

- در زمان بررسی، مخزن [eclipse-enclave/enclave](https://github.com/eclipse-enclave/enclave) حدود ۱۰۳ Star و ۲۱ Fork داشت و آخرین Push ثبت‌شده‌اش ۲۰ نوامبر بود. این آمار فقط وضعیت همان لحظهٔ مخزنه؛ به‌تنهایی نشانهٔ پذیرش گسترده در صنعت نیست.
- در گزارش اکتبر ۲۰۲۶ از عبارت عمومی «ai coding agent»، شاخص Google Trends برابر ۹ از ۱۰۰ گزارش شده؛ حدود ۲۹ درصد بالاتر از اکتبر سال قبل، اما هنوز ۹۰ درصد پایین‌تر از اوج ژوئن ۲۰۲۶. این داده از Google Trends از طریق DataForSEO گردآوری شده و به عبارت عمومی ایجنت کدنویسی مربوطه، نه جست‌وجوی مستقیم برای Sandbox.
- مستندات پروژه هم مرتب به‌روزرسانی شده‌اند؛ برای نمونه، در ۲۰ نوامبر تغییراتی دربارهٔ فیلتر کردن متغیرهای محیطی پروژه ثبت شده است.

پس بهتره از این شواهد نتیجهٔ «همه دارن از Sandbox استفاده می‌کنن» نگیریم. چیزی که می‌شه گفت اینه که اجرای خودمختار ایجنت‌ها به یک مسئلهٔ معماری و امنیتی واقعی تبدیل شده و ابزارهای تخصصی برای کنترلش در حال شکل‌گیری‌اند.

## اول تهدید رو دقیق تعریف کنیم

قبل از انتخاب Docker، Podman یا MicroVM باید مشخص کنیم قرار است جلوی چه چیزی رو بگیریم. یک مدل تهدید ساده برای ایجنت کدنویسی می‌تونه این موارد رو داشته باشه:

| تهدید | نمونهٔ آسیب |
| --- | --- |
| دسترسی بیش از حد به فایل‌ها | خواندن فایل‌های SSH، تنظیمات Cloud یا **.env** |
| اجرای کد غیرقابل‌اعتماد | اجرای Script یک Dependency یا فرمان مخرب |
| خروج اطلاعات از شبکه | فرستادن Source Code یا Token به یک دامنهٔ خارجی |
| تداخل نشست‌ها | تغییر فایل‌های یک تسک توسط ایجنت دیگر |
| دست‌کاری تنظیمات اجرا | تغییر تست‌ها، Hookها یا تنظیمات Build برای پنهان کردن خطا |
| باقی ماندن اطلاعات حساس | ذخیره شدن Prompt، تاریخچه یا Credential در Store پایدار |

این فهرست به معنی مخرب بودن خود ایجنت نیست. مدل ممکنه اشتباه کنه، متن مخرب رو دنبال کنه یا خروجی یک ابزار رو نادرست تفسیر کنه. در طراحی امنیتی بهتره فرض کنیم رفتار فرایند قابل‌پیش‌بینی نیست و محدودیت‌ها باید بیرون از مدل اعمال بشن.

## چهار مرز اصلی یک Agent Sandbox

من معماری رو به چهار سؤال تقسیم می‌کنم:

1. **See:** ایجنت چه فایل‌ها و اطلاعاتی رو می‌تونه ببیند؟
2. **Run:** کد ایجنت با چه سطح دسترسی و در چه محیطی اجرا می‌شه؟
3. **Reach:** ایجنت به کدام مقصدهای شبکه دسترسی داره؟
4. **Keep:** بعد از پایان نشست، چه اطلاعاتی باقی می‌مونه؟

در Eclipse Enclave هر نشست داخل محیط اجرایی جدا قرار می‌گیره، یک Worktree مشخص می‌تونه به آن وصل بشه، ترافیک خروجی از Gateway عبور می‌کنه و بخشی از وضعیت نشست روی میزبان باقی می‌مونه.

~~~mermaid
flowchart TD
    Dev["توسعه‌دهنده"] --> Host["کنترل‌کننده روی میزبان"]
    Host --> WT["Git Worktree اختصاصی"]
    Host --> Policy["تنظیمات و سیاست دسترسی"]
    WT --> Agent["Container ایجنت"]
    Policy --> Agent
    Agent --> Gateway["Gateway شبکه"]
    Gateway -->|مقصد مجاز| API["API و Registryهای مجاز"]
    Gateway -->|مقصد غیرمجاز| Deny["مسدودسازی و ثبت رویداد"]
    Agent --> Store["Store پایدار نشست"]
    Gateway --> Audit["Network Log"]
~~~

### ۱. مرز فایل‌ها: فقط چیزی رو Mount کن که لازم داری

Container به‌تنهایی جلوی دسترسی به فایل‌های میزبان رو نمی‌گیره؛ این Mountها هستن که مشخص می‌کنن چه چیزی داخل محیط اجرا دیده بشه.

اگر کل Home Directory رو Mount کنیم، عملاً بخش بزرگی از مرز امنیتی رو خودمون حذف کردیم. پوشه‌هایی مثل **~/.ssh**، **~/.aws**، **~/.config** و فایل‌های محیطی ممکنه Credential یا تنظیمات مهم داشته باشن. حتی Mount فقط‌خواندنی هم محرمانگی رو حفظ نمی‌کنه؛ ایجنت همچنان می‌تونه اطلاعات رو بخونه و از مسیر شبکه خارج کنه.

در Enclave، پروژه معمولاً به‌صورت Read/Write در اختیار نشست قرار می‌گیره و مسیرهای حساس به‌طور پیش‌فرض مسدود می‌شن. برای تحلیل کد بدون تغییر فایل‌ها می‌شه از حالت Read-only استفاده کرد:

~~~bash
enclave --project-mount readonly
~~~

برای اجرای چند کار هم‌زمان، بهتره هر ایجنت Worktree خودش رو داشته باشه:

~~~bash
git worktree add ../billing-agent-a -b agent/billing-a
git worktree add ../billing-agent-b -b agent/billing-b
~~~

حالا هر نشست روی مسیر و Branch جدا کار می‌کنه. این کار جلوی برخورد مستقیم تغییرات دو ایجنت رو می‌گیره، اما جای بازبینی و ادغام تغییرات رو نمی‌گیره.

یک نکتهٔ مهم: Worktree یک مرز امنیتی کامل نیست. اگر پوشهٔ پروژه قابل‌نوشتن باشه، ایجنت می‌تونه کد، تست، فایل‌های Build و بخشی از Metadata گیت رو تغییر بده. پس هر چیزی که داخل Workspace قرار می‌گیره باید در محدودهٔ اختیار ایجنت فرض بشه.

### ۲. مرز اجرا: Container با ماشین مجازی یکی نیست

Containerها با قابلیت‌هایی مثل Namespace و cgroup فرایندها و منابع رو جدا می‌کنن. این جداسازی برای بسیاری از کارهای توسعه مناسبه، اما Container معمولی Kernel میزبان رو با میزبان به اشتراک می‌ذاره. بنابراین نباید اون رو معادل یک مرز کامل Hypervisor در نظر بگیریم.

مستندات امنیتی خود Enclave هم صریح می‌گن که این ابزار یک مرز سخت‌شده برای جلوگیری از تمام Container Escapeها نیست. در تنظیم پیش‌فرض، Docker به‌صورت Rootful اجرا می‌شه؛ Podman در حالت Rootless پشتیبانی می‌شه و Rootless Docker در حال حاضر Backend پشتیبانی‌شده‌ای نیست.

برای میزبان‌هایی که Docker Rootful دارن، پروژه استفاده از User Namespace Remapping رو به‌عنوان یک لایهٔ سخت‌سازی پیشنهاد می‌کنه. این کار باعث می‌شه UID صفر داخل Container به یک UID غیرممتاز روی میزبان نگاشت بشه؛ البته ممکنه روی مالکیت فایل‌های Bind Mount و بعضی Dev Containerها اثر بذاره و باید قبل از استفاده در محیط کاری تست بشه.

اگر کد واقعاً غیرقابل‌اعتماد باشه، مثلاً می‌خوایم Pull Request ناشناخته یا اسکریپت شخص ثالث رو اجرا کنیم، یک VM یا محیط دوردست یک‌بارمصرف می‌تونه مرز قوی‌تری از Container معمولی فراهم کنه. اما انتخاب MicroVM به‌تنهایی کافی نیست؛ شبکه، Mountها و Credentialها همچنان باید محدود بشن.

### ۳. مرز شبکه: Allowlist خوبه، اما معجزه نمی‌کنه

یکی از قسمت‌های جالب معماری Enclave، Gateway جداگانه‌ایه که کنار Container ایجنت اجرا می‌شه. در حالت Restricted، این Gateway از DNS، Firewall و Proxy برای کنترل مقصدهای خروجی استفاده می‌کنه. دامنه‌های مجاز Resolve می‌شن و درخواست‌های HTTP/HTTPS هم بر اساس Host یا SNI دوباره بررسی می‌شن.

مثلاً اگر ایجنت برای دریافت یک Dependency به Registry مشخصی نیاز داشته باشه، می‌تونیم فقط همان مقصد رو به فهرست مجاز اضافه کنیم:

~~~bash
enclave --allow-domain registry.npmjs.org
~~~

این نمونه صرفاً برای نشان دادن نحوهٔ اضافه کردن دامنه است؛ در یک پروژهٔ واقعی باید تمام مقصدهای موردنیاز رو از روی رفتار Build و ابزارها شناسایی کنیم. باز کردن wildcardهایی مثل **\*.example.com** ممکنه دامنه‌های بیشتری از چیزی که لازم داریم در اختیار ایجنت بذاره.

اما اینجا یک محدودیت مهم وجود داره: **Allowlist دامنه، سیاست محتوای درخواست نیست.** اگر یک سرویس مجاز خودش قابلیت Proxy، Upload یا Relay داشته باشه، ایجنت ممکنه از همان سرویس برای انتقال اطلاعات استفاده کنه. طبق مستندات Enclave، IP مجاز می‌تونه روی Portهای دیگر هم قابل‌دسترسی باشه؛ ترافیک Portهای غیر از ۸۰ و ۴۴۳ از Proxy عبور نمی‌کنه و در Network Log هم ثبت نمی‌شه.

پس نباید نتیجه بگیریم که «هر چیزی در Log نیست، حتماً ارسال نشده». Log در این معماری شواهد مفیدی تولید می‌کنه، اما تمام ترافیک رو با یک سطح جزئیات ثبت نمی‌کنه.

برای مشاهدهٔ درخواست‌های مسدودشده می‌شه از این دستور استفاده کرد:

~~~bash
enclave network log --verdict deny
~~~

حالت ثبت جزئیات درخواست‌ها هم وجود داره، اما فعال کردن آن می‌تونه TLS رو در مسیرهای مجاز بررسی کنه و با بعضی Clientهایی که Certificate Pinning دارن سازگار نباشه. حالت Full Capture هم ممکنه Header، Body و محتوای پاسخ رو روی میزبان ذخیره کنه؛ بنابراین فایل‌های Capture رو باید مثل دادهٔ حساس نگهداری کنیم.

### ۴. مرز Credential: Secret رو به فرایند ایجنت تحویل نده

فرض کن ایجنت برای دسترسی به یک API به Token نیاز داره. راه ساده اینه که Token رو داخل Environment Variable قرار بدیم. اما هر فرایندی که به Environment دسترسی داشته باشه ممکنه بتونه اون رو بخونه یا در Log چاپ کنه.

در Enclave برای بعضی Credentialهای تعریف‌شده، Gateway می‌تونه مقدار واقعی رو از دید فرایند داخل Container پنهان نگه داره. ایجنت به‌جای مقدار واقعی یک Placeholder دریافت می‌کنه و Gateway فقط هنگام ارسال درخواست HTTPS به Host و Header مشخص‌شده، مقدار واقعی رو جایگزین می‌کنه.

این روش برای تمام Credentialها کار نمی‌کنه. اطلاعاتی که به شکل فایل در اختیار Container قرار می‌گیرن یا Secretهایی که Release Rule ندارن ممکنه همچنان برای ایجنت قابل‌دسترسی باشن. SSH هم مسیر جداگانه‌ای داره و ترافیک Port 22 از Proxy شبکه عبور نمی‌کنه.

برای همین، حتی با وجود Gateway هم بهتره:
- از Tokenهای کوتاه‌عمر و محدود به یک پروژه استفاده کنیم.
- Credentialهای Production رو در اختیار ایجنت توسعه قرار ندیم.
- دسترسی Read رو از Write جدا کنیم.
- برای عملیات مالی، انتشار و تغییر زیرساخت تأیید انسانی مستقل داشته باشیم.

## یک محدودیت مهم: MicroVM آزمایشی Enclave را با حالت Restricted اشتباه نگیریم

در مستندات Backendهای Enclave، گزینهٔ QEMU به‌عنوان یک MicroVM آزمایشی معرفی شده. ممکنه با دیدن عبارت MicroVM تصور کنیم این گزینه از نظر امنیتی در تمام ابعاد از Docker بهتره؛ اما وضعیت فعلی پروژه چنین نتیجه‌ای رو تأیید نمی‌کنه.

Backend آزمایشی QEMU در نسخهٔ مستندشده:
- فقط برای نشست‌های Foreground طراحی شده.
- روی معماری x86-64 اجرا می‌شه.
- Gateway شبکه نداره و Egress رو محدود نمی‌کنه.
- Network Log و Credential Release مبتنی بر Gateway رو ارائه نمی‌ده.
- بعضی قابلیت‌های Session و Featureهای Docker/Podman رو پشتیبانی نمی‌کنه.

پس اگر نیاز اصلی ما جلوگیری از خروج اطلاعات از شبکه است، صرفاً انتخاب QEMU به معنی رسیدن به هدف نیست. باید همهٔ ابعاد مرز امنیتی رو جداگانه ارزیابی کنیم: Kernel، فایل‌ها، شبکه، Secretها و وضعیت پایدار.

## چه معماری‌ای برای چه کاری مناسب‌تره؟

| سناریو | انتخاب منطقی | نکتهٔ مهم |
| --- | --- | --- |
| کار روزمره روی ریپوزیتوری قابل‌اعتماد | Container با Mount محدود و Egress کنترل‌شده | هر ایجنت Worktree خودش رو داشته باشه |
| تحلیل کد بدون تغییر | Workspace فقط‌خواندنی | Read-only محرمانگی رو تضمین نمی‌کنه |
| اجرای PR یا Dependency ناشناخته | VM یا محیط یک‌بارمصرف | بدون Credential و با شبکهٔ محدود |
| اجرای چند ایجنت موازی | Worktree و Session جدا | تغییرات باید قبل از Merge بررسی بشن |
| عملیات Production و مالی | محیط کنترل‌شده با تأیید انسانی | دسترسی مستقیم Write به ایجنت ندیم |

## یک چک‌لیست قبل از فعال کردن اجرای خودمختار

من قبل از اینکه یک ایجنت رو بدون تأیید مرحله‌به‌مرحله اجرا کنم، این موارد رو بررسی می‌کنم:

- [ ] برای هر تسک یک Branch یا Worktree مستقل ساخته شده.
- [ ] Home Directory، پوشهٔ SSH و تنظیمات Cloud به محیط Mount نشده‌اند.
- [ ] فایل‌های **.env**، تنظیمات Dev Container و Scriptهای پروژه بررسی شده‌اند.
- [ ] هیچ Credential واقعی Production در اختیار نشست نیست.
- [ ] شبکه در حالت Deny-by-default قرار داره و فقط مقصدهای ضروری باز شده‌اند.
- [ ] محدودیت‌های Port، Proxy و سطح جزئیات Network Log مشخص شده‌اند.
- [ ] تاریخچه و Store پایدار نشست مثل دادهٔ حساس نگهداری می‌شن.
- [ ] Extension یا ابزار جانبی قبل از نصب از نظر Scriptهای اجراشونده بررسی شده.
- [ ] Diff، تست‌ها و تغییرات مربوط به CI و Git Hookها قبل از Merge بازبینی می‌شن.

اگر یک مورد از این فهرست روشن نیست، بهتره سطح خودمختاری ایجنت رو پایین بیاریم یا محیط اجرای محدودتری بسازیم.

## جمع‌بندی

Sandbox قرار نیست ایجنت رو باهوش‌تر کنه؛ قرار است دامنهٔ آسیبی رو که یک اشتباه یا دستور مخرب می‌تونه ایجاد کنه محدود کنه. برای این کار باید فایل‌ها، فرایندها، شبکه، Credentialها و دادهٔ باقی‌مانده بعد از نشست رو جداگانه کنترل کنیم.

Eclipse Enclave نمونهٔ جالبیه چون این کنترل‌ها رو در یک Runtime مستقل از مدل و ابزار کدنویسی کنار هم قرار می‌ده. بااین‌حال، Container معمولی مرز سخت‌شدهٔ ضد Escape نیست، Allowlist تمام مسیرهای خروج داده رو نمی‌بنده و Backend آزمایشی QEMU هم در وضعیت فعلی Egress محدودشده نداره.

برای یک پروژهٔ واقعی، من از یک Worktree جدا، Mount محدود، Credential آزمایشی و Network Policy کوچک شروع می‌کنم. بعد از بررسی رفتار و لاگ‌ها، دامنهٔ دسترسی رو فقط به‌اندازهٔ نیاز گسترش می‌دم. **خودمختاری وقتی ارزش داره که محدودهٔ اختیارش از قبل مشخص باشه.**
