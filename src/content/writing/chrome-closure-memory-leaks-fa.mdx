فرض کن صفحهٔ گزارش‌گیری یک پنل مدیریتی رو باز می‌کنی. بار اول همه‌چیز روانه، ولی بعد از چند بار باز و بسته کردن فیلترها، مرورگر چندصد مگابایت بیشتر حافظه مصرف می‌کنه. صفحه رو هم عوض نکردی؛ فقط چند بار همون کار رو تکرار کردی.

اولین حدس معمولاً اینه که «حتماً یه آرایه رو پاک نکردیم». گاهی درسته، اما همیشه هم ردپای مشکل این‌قدر واضح نیست. ممکنه یک تابع کوچک که فقط شمارنده رو زیاد می‌کنه، ناخواسته باعث زنده موندن یک مجموعهٔ بزرگ داده بشه.

در به‌روزرسانی **November 2026 Chrome DevTools**، گوگل قابلیتی برای تشخیص **dead context fields** در Heap Snapshot معرفی کرده؛ متغیرهایی که دیگه هیچ Closure زنده‌ای ازشون استفاده نمی‌کنه، اما به‌خاطر ساختار Context مشترک هنوز در حافظه نگه داشته می‌شن. این تغییر رو بهانه می‌کنیم تا ببینیم واقعاً چطور باید نشت حافظه رو پیدا و رفع کرد.

## اول فرق مصرف حافظه با نشت حافظه رو بفهمیم

هر افزایش حافظه‌ای نشت نیست. مرورگر برای رندر، کش، کد و داده‌ها حافظه می‌گیره. موتور JavaScript هم معمولاً بلافاصله بعد از بی‌استفاده شدن هر شیء، Garbage Collection انجام نمی‌ده.

نشانهٔ مهم‌تر اینه: **بعد از پایان یک عملیات و برگشتن برنامه به وضعیت قبلی، اشیایی که باید آزاد شده باشن همچنان قابل دسترسی باقی بمونن.** اگر این اتفاق با تکرار عملیات ادامه پیدا کنه، احتمال نشت بیشتره.

برای همین، فقط به عدد Memory در Task Manager نگاه نکن. نمودار مصرف حافظه می‌تونه بالا و پایین بره، اما باید بفهمیم کدوم شیء زنده مونده و **چه مرجعی نگهش داشته**.

## Closure چطور یک شیء بزرگ رو نگه می‌داره؟

Closure یعنی تابعی که می‌تونه به متغیرهای محیط تعریف خودش دسترسی داشته باشه؛ حتی وقتی اجرای تابع بیرونی تموم شده.

این مثال عمداً یک الگوی پرخطر رو نشون می‌ده:

```js
function createReportController(rows) {
  const index = new Map(rows.map((row) => [row.id, row]));
  let page = 1;

  function findRow(id) {
    return index.get(id);
  }

  function nextPage() {
    page += 1;
    return page;
  }

  return { findRow, nextPage };
}

const controller = createReportController(largeReportRows);
```

اینجا نگه داشتن `index` طبیعی و لازمه؛ چون `findRow` هنوز ازش استفاده می‌کنه. پس این کد به‌تنهایی **نشت حافظه نیست**. اگر `controller` عمر طولانی داشته باشه، داده‌ها هم باید تا وقتی `findRow` در دسترسه باقی بمونن.

حالا فرض کن بعداً فقط `nextPage` رو نگه داریم و فکر کنیم `index` دیگه مصرفی نداره. بسته به نحوهٔ مدیریت محیط‌های لغوی و بهینه‌سازی موتور، Context مشترک Closureها می‌تونه باعث بشه داده‌هایی که عملاً مصرف نمی‌شن همچنان نگه داشته بشن. جزئیات دقیق به نسخهٔ موتور، الگوی دسترسی و خروجی Heap Snapshot بستگی داره؛ بنابراین از روی کد به‌تنهایی نباید حکم قطعی داد.

قابلیت جدید Chrome دقیقاً برای کمک به شناسایی بخشی از همین وضعیت‌هاست: **فیلدهای بلااستفادهٔ Context که هنوز به‌خاطر Closureهای دیگر نگه داشته شده‌اند**.

## چه چیزی در Chrome DevTools تازه شده؟

طبق [یادداشت رسمی Chrome برای نوامبر ۲۰۲۶](https://developer.chrome.com/blog/new-in-devtools-november-2026)، پنل Memory حالا با استفاده از metadata مربوط به Scope در Heap Snapshot، Closureها رو با Contextهای مشترک مرتبط می‌کنه و فیلدهایی رو که هیچ Closure زنده‌ای نمی‌خونه، ولی همچنان نگه داشته شده‌اند، مشخص می‌کنه. نمایش این موارد بر اساس اثرشون روی حافظه مرتب می‌شه.

این قابلیت یک «دکمهٔ رفع نشت» نیست. تشخیص می‌ده کجا باید بررسی کنیم؛ هنوز باید ثابت کنیم اون داده‌ها واقعاً بعد از اتمام کار لازم نیستن.

تفاوت مهمش با ابزارهای قدیمی اینه که قبلاً بیشتر دنبال شیءهای بزرگ، Detached DOM و مسیر Retainer می‌گشتیم. حالا می‌تونیم سرنخ دقیق‌تری دربارهٔ **متغیر بلااستفاده داخل Context مشترک** داشته باشیم.

## یک مثال واقعی‌تر: Handler قدیمی صفحه

این نمونه برای نمایش یک نشت قابل پیش‌بینی نوشته شده:

```js
function mountReport(button, rows) {
  const lookup = new Map(rows.map((row) => [row.id, row]));
  const onClick = () => {
    console.log("Loaded rows:", lookup.size);
  };

  button.addEventListener("click", onClick);

  // اشتباه: هیچ راهی برای آزاد کردن listener نداریم.
}
```

اگر `button` برای مدت طولانی در صفحه بمونه و هر بار `mountReport` رو صدا بزنیم، Listenerهای قبلی هم باقی می‌مونن. هر Listener به `lookup` خودش دسترسی داره و داده‌های قدیمی رو نگه می‌داره.

اصلاح ساده‌اش اینه که طول عمر Listener رو صریح مدیریت کنیم:

```js
function mountReport(button, rows) {
  const lookup = new Map(rows.map((row) => [row.id, row]));
  const controller = new AbortController();

  button.addEventListener(
    "click",
    () => console.log("Loaded rows:", lookup.size),
    { signal: controller.signal },
  );

  return () => controller.abort();
}

const dispose = mountReport(button, rows);
// موقع خروج از صفحه یا جایگزینی گزارش:
dispose();
```

این اصلاح وقتی کار می‌کنه که `dispose` واقعاً در زمان مناسب اجرا بشه و جای دیگری هم به داده‌ها مرجع نداشته باشیم. صرف استفاده از `AbortController` تضمین نمی‌کنه تمام حافظهٔ برنامه آزاد بشه.

## روش مرحله‌به‌مرحلهٔ پیدا کردن نشت حافظه

من برای چنین مشکلی این مسیر رو می‌رم:

1. **سناریو رو قابل تکرار کن.** مثلاً گزارش رو باز کن، فیلتر بزن، ببند و این کار رو ده بار تکرار کن. همون داده‌ها و همون مسیر رو نگه دار.
2. **یک وضعیت پایه ثبت کن.** در Chrome DevTools، پنل Memory رو باز کن و از Heap Snapshot استفاده کن. اگر برنامه هنوز در حال لود یا دریافت داده‌ست، صبر کن تا وضعیت پایدار بشه.
3. **عملیات و عکسش رو انجام بده.** پنل رو باز و بسته کن؛ فقط باز کردن پنل معیار خوبی نیست، چون ممکنه داده‌ها عمداً تا پایان نمایش نگه داشته بشن.
4. **Snapshot دوم رو بگیر و مقایسه کن.** در Comparison، تعداد و اندازهٔ اشیای باقی‌مانده رو ببین. دنبال رشد تکرارشونده باش، نه صرفاً یک اختلاف کوچک.
5. **مسیر Retainer رو دنبال کن.** ببین چه چیزی هنوز به شیء موردنظر اشاره می‌کنه: یک Listener، کش، متغیر سراسری، DOM جداشده یا Closure.
6. **Dead context fields رو هم بررسی کن.** در نسخه‌های پشتیبانی‌شدهٔ DevTools، سرنخ‌های Context مشترک رو کنار مسیر Retainer تحلیل کن.
7. **کد رو اصلاح و همون آزمایش رو تکرار کن.** معیار موفقیت فقط کاهش یک عدد نیست؛ اشیای مربوط به عملیات تمام‌شده نباید بعد از تکرار سناریو بی‌دلیل انباشته بشن.

[راهنمای رسمی Heap Snapshot](https://developer.chrome.com/docs/devtools/memory-problems/heap-snapshots) روش Comparison و Retainers رو توضیح داده. برای پیدا کردن Detached DOM هم [راهنمای Memory Problems](https://developer.chrome.com/docs/devtools/memory-problems) مثال‌های مستقلی داره.

## Shallow Size و Retained Size چه فرقی دارن؟

| معیار | معنی | برداشت درست |
| --- | --- | --- |
| Shallow Size | حافظهٔ خود شیء | شیء کوچک لزوماً کم‌هزینه نیست |
| Retained Size | حافظه‌ای که با حذف دسترسی به شیء، بالقوه قابل آزاد شدن می‌شه | برای پیدا کردن گره‌های نگه‌دارنده مفیده |
| Retainers | مرجع‌هایی که شیء رو زنده نگه می‌دارن | سرنخ اصلی برای رسیدن به علت |
| Comparison | تغییر اشیا بین دو Snapshot | برای بررسی رشد پس از عملیات تکراری مفیده |

یک تابع کوچک ممکنه Shallow Size ناچیزی داشته باشه، اما به ساختاری اشاره کنه که حجم زیادی از حافظه رو نگه داشته. البته Retained Size رو هم نباید به‌عنوان مقدار دقیق حافظه‌ای که فوراً به سیستم‌عامل برمی‌گرده تفسیر کنیم.

## در React و SPAها کجا بیشتر باید مراقب باشیم؟

وقتی یک کامپوننت Unmount می‌شه، انتظار داریم اشتراک‌ها و Listenerهای مختص اون هم پاک بشن. مثال زیر برای اتصال به رویداد عمومی مرورگره:

```tsx
import { useEffect } from "react";

function ReportViewport() {
  useEffect(() => {
    const onResize = () => {
      // اندازهٔ نمودار را با viewport هماهنگ کن
    };

    window.addEventListener("resize", onResize);
    return () => window.removeEventListener("resize", onResize);
  }, []);

  return <section>Report</section>;
}
```

اما Cleanup فقط یکی از قسمت‌های مسئله‌ست. اگر کشی سراسری بدون محدودیت رشد کنه، یا Promiseهای قدیمی بعد از عوض شدن صفحه همچنان دادهٔ بزرگی رو نگه دارن، باید طول عمر اون‌ها رو هم بررسی کنیم.

در یک SPA بهتره برای هر عملیات سنگین مشخص باشه **مالک داده کیه، داده تا چه زمانی لازمه و چه اتفاقی باعث آزاد شدنش می‌شه**. این سؤال‌ها معمولاً از اضافه کردن یک ابزار مانیتورینگ تازه مؤثرترن.

## چند اشتباه رایج هنگام تحلیل

- **هر رشد حافظه‌ای رو Leak حساب نکن.** کش عمدی و Garbage Collection زمان‌بندی‌شده می‌تونن نمودار رو تغییر بدن.
- **یک Snapshot کافی نیست.** بدون سناریوی قابل تکرار و مقایسه، تشخیص علت سخت می‌شه.
- **همه‌چیز رو به Closure نسبت نده.** Detached DOM، Timer، Listener و کش‌های بدون سقف هم رایجن.
- **دادهٔ حساس رو بی‌فکر در Snapshot ذخیره نکن.** Heap Snapshot ممکنه شامل رشته‌ها و داده‌های واقعی کاربر باشه؛ مثل یک خروجی حساس باهاش رفتار کن.
- **به ابزار به چشم حکم نهایی نگاه نکن.** Dead context field یک سرنخه، نه اثبات اینکه حذفش همیشه درسته.

## برای یک تیم توسعه، از کجا شروع کنیم؟

لازم نیست از روز اول تست حافظهٔ پیچیده وارد CI کنیم. اول یک مسیر پرمصرف انتخاب کن: باز و بسته کردن یک Modal بزرگ، رفت‌وآمد بین دو Route یا بارگذاری مجدد یک DataGrid. تعداد تکرارها و نسخهٔ مرورگر رو ثبت کن، Snapshot بگیر و نتیجه رو بعد از اصلاح مقایسه کن.

اگر مشکل فقط در استفادهٔ طولانی ظاهر می‌شه، تست کوتاه ممکنه چیزی نشون نده. سناریو باید شبیه رفتار واقعی کاربر باشه و زمان کافی برای جمع‌آوری زباله و پایان درخواست‌های معلق در نظر بگیره.

در نهایت، نکتهٔ مهم این قابلیت تازهٔ Chrome این نیست که از امروز تمام نشت‌های حافظه خودکار پیدا می‌شن. ارزشش اینه که یک لایهٔ کمتر قابل مشاهده از ارتباط Closureها و Contextهای مشترک رو روشن‌تر می‌کنه. هنوز بهترین روش همون مسیر قدیمیه: **بازسازی مشکل، مقایسه، دنبال کردن مرجع‌ها، اصلاح و اندازه‌گیری دوباره**.
