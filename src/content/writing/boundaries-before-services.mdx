Splitting an application into services creates independent deployment units. It also creates network boundaries, partial failures, and coordination costs.

## Begin with responsibilities

Write down what each part owns and which decisions it can make without consulting another part. If two components continually need each other’s internal data, their boundary may be misplaced.

## Follow the transaction

Consider a business operation that changes several records. Moving those records into different services changes what can be committed atomically. That is a business behavior decision as well as a technical one.

## Make the trade-off explicit

Independent scaling or team ownership can justify a new service. A smaller code folder on its own usually cannot. A modular application can preserve useful boundaries while keeping deployment and transactions simpler.
