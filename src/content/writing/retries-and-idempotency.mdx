A timeout tells a client that it did not receive an answer. It does **not** tell the client whether the operation happened.

That distinction matters when an operation moves money. Retrying a request without a stable identity can turn one intended payment into two operations.

## Give the operation an identity

The client can attach an idempotency key to each logical operation. When a retry arrives, the service looks up that identity and returns the stored outcome instead of executing it again.

```http
POST /payments
Idempotency-Key: order-123-attempt-1
Content-Type: application/json

{"amountMinor": 25000, "currency": "IRR"}
```

The key belongs to the logical operation, not to each network attempt. Scope it to the authenticated caller and reject a reused key whose request parameters differ.

## Persistence is the hard part

A lookup followed by a separate insert is vulnerable to concurrent requests. Enforce uniqueness in durable storage, and design the relationship between the idempotency record and the business transaction deliberately.

<Callout title="An example, not a complete payment design">
A production implementation also needs retention rules, recovery for in-progress requests, authorization checks, and reconciliation with external systems. An idempotency key alone does not make a distributed operation exactly-once.
</Callout>

## Start with the ambiguous outcome

Ask what happens if the service commits the operation and then loses its connection before responding. Walk through that failure before choosing a retry policy. It exposes the assumptions that a happy-path test will miss.
